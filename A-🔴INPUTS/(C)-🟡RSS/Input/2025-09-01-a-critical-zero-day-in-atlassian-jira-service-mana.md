May peace and justice be restored soon.<br /><strong><em>always free Palestine</em>🇵🇸🇵🇸</strong></p><h3>Introduction</h3><p>Hello Folks, my name is <strong>Mo Salah</strong>. I’m a security researcher and bug bounty hunter with a passion for finding vulnerabilities in real-world applications. Over the years, I’ve tested many platforms and services, focusing mainly on <strong>web application security, access control flaws, and cloud-based environments</strong>.</p><p>In this blog, I’ll share one of my findings — a critical vulnerability I discovered in <strong>Atlassian Jira Service Management Cloud</strong> — and walk you through how I identified it, validated it, and reported it responsibly</p><h3><strong><em>What is Jira Service Management (JSM) Cloud?</em></strong></h3><p>Jira Service Management Cloud is an online tool created by Atlassian that helps companies manage customer support and internal requests. It’s like a digital helpdesk where employees or customers can report issues, ask for help, and track progress until the problem is solved.</p><h3>Let’s start from the beginning…</h3><p>While testing my favorite program<strong>(external program</strong>) in a bug bounty, I noticed that one of its subdomains was running on <strong>Jira Service Management Cloud</strong>. Since this platform is widely used by organizations to manage customer support requests, I decided to take a closer look and perform some security testing.</p><p>I began with common checks such as <strong>Broken Access Control</strong>, <strong>CSRF</strong>, and other typical web vulnerabilities, but I didn’t find anything impactful at first. Then, I turned my attention to the <strong>password reset functionality</strong></p><h3><em>The Reset Password Flow…</em></h3><p>Normally, password reset flows are very straightforward:</p><p>- A user requests a password reset for their account (e.g.,<strong>free@Palestine.com</strong>).<br />- Jira Service Cloud sends a reset token to the user’s registered email inbox.<br />- The user clicks the link, enters a new password, and the process is complete</p><p>That’s how it should work. But in this case, something unusual happened when I tested the flow more deeply.</p><h3>Exploitation</h3><p>While testing this process, I used an interception proxy (Burp Suite) to inspect the HTTP request when submitting the new password. I noticed something : The <strong>request body contained an `email` parameter</strong>.</p><pre>POST /reset-password<br />Host: &lt;jira-portal&gt;<br />Content-Type: application/json<br />{<br /> &quot;email&quot;: &quot;free@Palestine.com&quot;,<br /> &quot;newPassword&quot;: &quot;NewPassword123!&quot;<br />}</pre><p>By replacing my own email with `victim@gmail.com`, the server accepted the request — and the victim’s password was updated to the one I provided.</p><p>After reproducing the bug on the external program I tested, I wanted to make sure it wasn’t just a <strong>configuration issue</strong> specific to their Jira Service Management setup. To exclude this possibility, I created an <strong>independent JSM Cloud instance</strong> using a free Atlassian subscription.</p><p>I set up a Jira Service Management project with the <strong>default options enabled </strong>— especially the portal only account <strong>registration setting</strong>. Then, I repeated the same steps, and the bug was still there.</p><h3>Step To Reproduce</h3><p>Created a Jira Service Management portal with default settings, including portal-only account registration.</p><p>1- Create accounts <strong>A and B</strong> on <strong>Jira Service Management Cloud</strong></p><p>2- Go to reset password page and Request a password reset for <strong>account A</strong>.</p><p>3- A<strong>ccount A</strong> received a password reset link and clicked it.</p><p>4- Enter the new password, intercept the request with Burp, and change the email parameter to “<strong>B email</strong>”.</p><p>5- User<strong> B’s</strong> password has been changed.</p><p>6- Now log in with <strong>Account B</strong> using the new password.</p><h3><em>Impact</em><strong>…</strong></h3><p>This vulnerability allowed:<br />1- <strong>Full Account Takeover</strong> — Any Jira Service Cloud account could be hijacked.<br />2- <strong>No User Interaction Required</strong> — Once an attacker had their own valid reset token, they could directly target any victim by changing the `email` field.<br />3- <strong>Widespread Effect</strong>— Because this flaw existed at the <strong>product level</strong>, every organization running Jira Service Management Cloud was affected.<br /><br /> In other words, it was a <strong>universal password reset vulnerability</strong> across JSM Cloud platform.</p><p>Finally, The company’s security team triaged the report, resolved the bug within 20 minutes, and rewarded me
