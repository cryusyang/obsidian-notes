<h3>About Me</h3><p>Hello, I’m <strong>Aland Dlshad</strong>, also known as <strong>HexaPHP</strong>.<br /> I’m a <strong>cybersecurity specialist</strong> with a focus on <strong>web application penetration testing</strong>. My work involves identifying vulnerabilities, improving security, and staying ahead of emerging cyber threats.</p><h3>My Journey</h3><p>Hello guys,<br />While testing a production website with an estimated $150 million in annual revenue</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/905/1*Mb3tMwE2sfg87iKbIhz8LA.jpeg" /></figure><p>I decided to review the <strong>password reset system</strong>.</p><p>I created a normal account and noticed that each user was assigned a <strong>sequential numeric account ID</strong>.</p><p>For example, my account ID was: 9546525</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/626/1*eSJWpPU2jg7WBL_73pU-jA.jpeg" /></figure><p>By increasing and decreasing the account number in the <strong>Forgot Password (by Account ID)</strong> flow, I was able to access other users’ reset processes, confirming an <strong>IDOR (Insecure Direct Object Reference)</strong> vulnerability.</p><h3>Password Reset Flow</h3><p>The platform allowed password resets using:</p><p>Email</p><p>Account Id</p><p>Using the Account ID option, I was able to target <strong>any user</strong> simply by changing the numeric value.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/459/1*vlPl4n8uHPJmQ8Vgp7B4bw.jpeg" /></figure><h3>OTP Verification Request</h3><p>During the reset process, the following request was sent:</p><pre>POST /authentication/login?handler=VerifyCode HTTP/2<br />code=1111</pre><figure><img alt="" src="https://cdn-images-1.medium.com/max/798/1*z_9jZbqlFI_pNl9dcpHzDg.jpeg" /></figure><p>The server responded:</p><pre>{<br />  &quot;redirectUrl&quot;: &quot;&quot;,<br />  &quot;errorMessage&quot;: &quot;The verification code you entered is not valid.&quot;,<br />  &quot;success&quot;: false,<br />  &quot;result&quot;: 0,<br />  &quot;resultCode&quot;: 0<br />}</pre><h3>Response Manipulation (Logic Flaw)</h3><p>The application relied on the client-side success value.</p><p>By modifying:</p><pre>&quot;success&quot;: false</pre><p>to:</p><pre>&quot;success&quot;: true</pre><p>the system accepted the verification and allowed me to proceed to the password reset page.</p><p>No valid OTP was required.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/556/1*5sycxRVbftUjQ4PUqMtRZA.jpeg" /></figure><h3>Zero‑Click Account Takeover</h3><p>By chaining the <strong>IDOR vulnerability</strong> with the <strong>OTP logic flaw</strong>, I was able to:</p><ul><li>Reset any user’s password</li><li>Log in as any account</li><li>Fully take over user profiles</li></ul><p>This required <strong>no interaction from the victim</strong>, making it a <strong>zero‑click Account Takeover</strong>.</p><h3>Impact</h3><p>This issue allowed full account compromise across the platform and posed a serious risk to:</p><ul><li>User data</li><li>Account security</li><li>Business trust</li></ul><p>Because the website generates around <strong>$150 million in revenue</strong>, the potential damage was extremely high.</p><h3>Responsible Disclosure</h3><p>I documented the vulnerability with screenshots and network logs and reported it responsibly to the company so they could fix the issue.</p><h3>Final Result</h3><p>The issue was validated and resolved.<br /> For this discovery, I received a <strong>$4,000 reward</strong>.</p><h3>Contact</h3><p>If you’d like to connect or learn more about my work:<br /> <a
