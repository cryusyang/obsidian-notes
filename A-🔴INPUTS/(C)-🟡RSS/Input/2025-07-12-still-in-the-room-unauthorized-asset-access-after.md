<h3>Still In the Room — Unauthorized Asset Access After Removal</h3><figure><img alt="" src="https://cdn-images-1.medium.com/max/640/1*Ct8hXvUHdE3xgWCjM9nEOw.gif" /></figure><p>I’d like to share a simple bug that surprisingly gets overlooked quite often.</p><p>I initially thought this was just another low-hanging fruit — and honestly, it kind of is — but after testing it across multiple programs, I noticed that I rarely received duplicates. That’s when I realized it’s worth sharing.</p><p>The vulnerability allows a <strong>former member</strong> of an organization to continue <strong>viewing newly uploaded assets</strong> (like images or code files) even after being removed from the org.<br /> While they can’t upload anything, they can still access files that are uploaded after their access has been revoked.</p><p>This happens because the asset URLs are publicly accessible — <strong>no authentication is required</strong>.<br /> After analyzing the structure of the asset URLs, I found that I could guess new file links using a consistent URL pattern — even though I was no longer a member.</p><p>The URL format usually looked like this:</p><p><a href="https://assets.example.com/org-uuid/project-uuid/asset-uuid/123456image.png">https://assets.example.com/org-uuid/project-uuid/asset-uuid/123456image.png</a></p><h3>So what’s happening here?</h3><p><strong>org-uuid</strong><br /> This is the unique identifier of the organization. It usually stays the same as long as you're referencing assets from the same org.</p><p><strong>project-uuid</strong><br /> This is the UUID of a specific project within the organization.</p><p><strong>asset-uuid</strong><br />This represents the <strong>asset container</strong> — essentially the folder or path where uploaded files are stored.<br /> I noticed that <strong>each project has a fixed asset UUID</strong> that doesn’t change over time.<br /> Once the project is created, all files uploaded within it go under the same asset-uuid.<br /> This makes it easier for an attacker who had prior access to reuse that UUID and guess new file links.</p><p><strong>123456image.png</strong><br /> This is the actual filename. The prefix 123456 is typically a 6-digit numeric file ID that increases sequentially as new files are uploaded. This part is often predictable or guessable.</p><h3>Putting it all together</h3><p>After analyzing the URL structure, I noticed that the org-uuid, project-uuid, and asset-uuid were always the same — they didn’t change as long as the files were uploaded under the same organization and project.</p><p>Once I understood this, things got much easier.</p><p>Since these UUIDs were static, the only dynamic part of the link was the file ID — a simple 6-digit number. That meant I could <strong>brute-force or guess only the last part</strong> of the URL to access newly uploaded assets, even after losing membership access.</p><p>In short, I didn’t need to guess the full URL — just the file ID.</p><h3>Conclusion</h3><p>This bug is a clear example of how relying on obscurity — such as UUIDs or complex URLs — does <strong>not</strong> equate to real security.<br /> Access to sensitive files must be protected by <strong>proper authentication and authorization</strong>, especially when user roles change or accounts are removed.</p><p>Simple bugs like this can easily lead to <strong>data leakage</strong> and <strong>privacy issues</strong> if left unaddressed.</p><p><strong>Stay sharp, and never underestimate the small details.</strong></p><p>🔗 HackerOne: <a href="https://hackerone.com/0xoroot">https://hackerone.com/0xoroot</a><br /> 🔗 LinkedIn: <a href="https://www.linkedin.com/in/0xammaryasser/">https://www.linkedin.com/in/0xammaryasser/</a></p><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=61547097ed86" width="1" />
