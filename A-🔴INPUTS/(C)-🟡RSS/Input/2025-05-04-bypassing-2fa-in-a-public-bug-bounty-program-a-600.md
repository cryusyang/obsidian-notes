<p>As a bug bounty hunter, uncovering vulnerabilities in public programs is both thrilling and rewarding. In this post, I’ll walk you through how I discovered and exploited a 2FA bypass vulnerability in a public bug bounty program (anonymized as redacted.com for confidentiality), earning a total of $6000. I’ll share technical details, including a sample HTTP request for context, and insights from the retesting phase.</p><h3>The Initial Discovery: Bypassing OTP Verification</h3><p>The journey began with a standard login process on redacted.com. After entering valid credentials, the web application prompted for a one-time password (OTP) as part of its two-factor authentication (2FA) mechanism. To analyze the process, I ran Burp Suite in the background to intercept HTTP requests.</p><p>Here’s what I did:</p><ol><li><strong>Intercepted the OTP Request</strong>: I entered a random OTP, captured the request in Burp Suite’s Proxy tab, and sent it to the Repeater module for further analysis.</li><li><strong>Dropped the Request</strong>: Instead of forwarding the OTP request, I dropped it entirely.</li></ol><p>3<strong>. Analyzed the Request</strong>: The OTP verification request included a JSON Web Token (JWT) in the Authorization header, which was generated <em>before</em> the OTP was validated. This was a critical flaw, as the JWT appeared to grant access to authenticated endpoints.</p><p>Below is a sanitized example of the intercepted HTTP request for context:</p><pre>POST /api/verify-otp HTTP/1.1<br />Host: redacted.com<br />Content-Type: application/json<br />Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoiMTIzNDU2Nzg5MCIsImlhdCI6MTcyODAwMDAwMCwiZXhwIjoxNzI4MDAzNjAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c<br />Connection: close<br /><br />{<br />  &quot;otp&quot;: &quot;123456&quot;<br />}</pre><p>The JWT token in the Authorization header was the key. By dropping the OTP verification request, I hypothesized that the token might still be valid for accessing other endpoints.</p><h3>Exploring API Endpoints with GAP and Intruder</h3><p>To test the extent of the vulnerability, I used Burp Suite’s <strong>Get All Parameters (GAP)</strong> extension to enumerate all API endpoints associated with redacted.com. Then, I leveraged Burp’s <strong>Intruder</strong> tool to systematically send requests to these endpoints, including the JWT token in the Authorization header.</p><p>Surprisingly, I gained access to <em>all</em> API endpoints without completing the OTP verification. This was a significant security flaw, as it effectively bypassed the 2FA mechanism entirely.</p><h3>Reporting and Reward</h3><p>I responsibly reported the vulnerability to the program, detailing the steps to reproduce and the potential impact (e.g., unauthorized access to sensitive user data or actions). The company acknowledged the issue, fixed the bug, and awarded me <strong>$4000</strong> for the initial finding.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/797/1*lp8_EmkGDfNElAbYN51Oyw.png" /></figure><h3>Retesting: A Persistent Payment Endpoint Flaw</h3><p>After the fix, I retested the application (after 1 year) to ensure the vulnerability was resolved. The OTP verification process now appeared more robust, and most endpoints redirected unauthenticated requests to the OTP page. However, I decided to explore further using a different approach: <strong>browser forcing</strong>.</p><p>Instead of interacting with the OTP prompt in the browser, I manually navigated to the payment/order page (/payment/order) by directly entering the URL. To my surprise, this endpoint was still accessible without OTP verification. I could view and interact with the payment functionality, which was a critical oversight.</p><p>For context, here’s a sample HTTP request to the payment endpoint:</p><pre>GET /payment/order/transection HTTP/1.1<br />Host: redacted.com<br />Cookie:<br />Connection: close</pre><p>I tested other endpoints, but they correctly redirected to the OTP page. The payment/order/transection endpoint was the only one still vulnerable, indicating an incomplete fix.</p><h3>Second Report and Additional Reward</h3><p>I submitted a follow-up report, highlighting the persistent issue with the payment/order endpoint. The company promptly addressed the oversight and awarded me an additional <strong>$2000</strong>, bringing the total bounty to <strong>$6000</strong>.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*65nfF9rHIVhk6MI3VRAMqg.png" /></figure><h3>Key Takeaways</h3><p>This experience underscored several important lessons for bug bounty hunters and developers alike:</p><ol><li><strong>Test Beyond the Obvious</strong>: Dropping requests or bypassing UI prompts (e.g., browser forcing) can reveal hidden vulnerabilities.</li><li><strong>Enumerate Endpoints Thoroughly</strong>: Tools like GAP and Intruder are invaluable for discovering unprotected endpoints.</li><li><strong>Retest After Fixes</strong>: Incomplete patches can leave critical endpoints exposed, as seen with the payment/order page.</li><li><strong>Responsible Disclosure</strong>: Clear, detailed reports help companies fix issues effectively and reward hunters fairly.</li></ol><p>For developers, this case highlights the importance of validating authentication and authorization at every endpoint, especially for sensitive functionality like payments. Generating JWTs before completing 2FA checks is a recipe for disaster.</p><h3>Conclusion</h3><p>Finding and exploiting this 2FA bypass was a rewarding journey, both financially and intellectually. It reinforced the value of persistence, creative testing, and thorough retesting in bug bounty hunting.
