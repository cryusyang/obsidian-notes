> 本文描述了一次跨站脚本（XSS）漏洞的发现过程：作者通过漏洞赏金计划（VDP）对.NET应用进行测试，结合路径模糊测试（fuzzing）和对HTTP响应细节（如Content-Length）的敏锐观察，发现某页面虽返回“Invalid request”但实际接受GET请求。进一步分析源码后，作者在隐藏输入字段中构造出需特定快捷键触发的XSS payload，成功弹出恶意窗口。文章强调不应轻信400等HTTP错误状态码，持续深入挖掘往往能发现关键漏洞。

<p><strong>About XSS?<br /></strong>Cross-Site Scripting is a type of vulnerability that allows an attacker to inject JavaScript code into an application, deceiving the application into treating it as legitimate code. This can be exploited for malicious purposes, including stealing session cookies, credentials, credit card information, and more.</p><p><strong>How did I discover it?<br /></strong>I embarked on a cybersecurity adventure by selecting a VDP with an extensive scope. With curiosity as my guide, I randomly picked an endpoint, only to find it leading to yet another. But instead of turning back, I thought, ‘Let’s fuzzing; who knows what intriguing discoveries lie ahead?<br />After examining several routes, I determined that the application was built using the .NET framework. This led me to perform fuzzing again, but this time using extensions such as .asp and .aspx.</p><figure><img alt="Fuzzing" src="https://cdn-images-1.medium.com/max/756/1*hRJbKC9YCf8Frso34OVKIA.png" /><figcaption>Fuzzing with extensions</figcaption></figure><p>Upon visiting the page, an intriguing message, ‘<strong>Invalid request was submitted.</strong>’ caught my eye, seemingly devoid of any functions. Yet, the response, as revealed by ffuf, displayed a Content-Length of 2676. This prompted me to delve into the source code, driven by curiosity.</p><pre>&lt;form name=&quot;frmMain&quot; action=&quot;/refer.asp&quot; method=&quot;post&quot;&gt;<br />  &lt;input id=&quot;l&quot; name=&quot;hOK&quot; type=&quot;HIDDEN&quot; value=&quot;&quot;&gt;  <br />  &lt;input type=&quot;hidden&quot; name=&quot;l&quot; value=&quot;&quot;&gt;<br />&lt;/form&gt;</pre><p>While examining the source code, it was clear that the form was designed to be submitted using the POST method. Yet, curiosity led us to wonder: what if we attempted to send it using GET? The result was rather unexpected — the request was accepted</p><p>At that moment, a memory stirred — Gareth Heyes’ article on XSS lurking within hidden parameters. Intrigued, I revisited it with a fresh perspective, setting out to craft the perfect payload.</p><p><a href="https://portswigger.net/research/xss-in-hidden-input-fields">XSS in hidden input fields</a></p><p>After experimenting with some payloads, success came knocking as I managed to trigger the much-sought-after popup using the following payload:</p><pre>l=default&quot; accesskey=&quot;X&quot; onclick=&quot;alert(document.domain)</pre><p>It’s worth highlighting that for this vector to work, we need to convince the user to press a specific key combination. In Firefox on Windows/Linux, it’s ALT+SHIFT+X, and on OS X, it’s CTRL+ALT+X.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/817/1*1k3UJ1_eHyHDsq7xZ9Y0og.png" /></figure><p>In the source code, it would appear somewhat like this:</p><pre>#Before Inject<br />&lt;input type=&quot;hidden&quot; name=&quot;l&quot; value=&quot;&quot;&gt;<br /><br />#After Inject<br />&lt;input type=&quot;hidden&quot; name=&quot;l&quot; value=&quot;default&quot; accesskey=&quot;X&quot; onclick=&quot;alert(document.domain)&quot;&gt;</pre><p><em>An interesting takeaway from this journey was the encounter with several 400 errors. Despite these hurdles, I managed to unearth an XSS vulnerability. The lesson here? Don’t always take HTTP status codes like 400, 404, or 500 at face value. Keep forging ahead in your quest, and happy hunting!</em></p><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=0c8bf8fa43f9" width="1" />
