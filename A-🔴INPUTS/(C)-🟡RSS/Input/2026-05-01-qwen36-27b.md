> [!example] AI 摘要
> Qwen3.6-27B是阿里巴巴云推出的270亿参数稠密型原生多模态大模型，支持文本、图像和视频统一理解，具备128k原生上下文窗口与可切换的“思考/非思考”模式。该模型在多项代理式编程基准测试（如SWE-bench、Terminal-Bench 2.0、Claw-Eval）中全面超越前代397B总参/17B激活参数的MoE旗舰模型Qwen3.5-397B-A17B，同时模型体积仅约55.6GB，Q4_K_M量化后仅16.8GB，可在单块24GB消费级GPU或最新Apple Silicon设备上本地运行。其稠密架构简化部署，避免MoE路由复杂性，但在超长上下文（>64k）性能衰减较明显，适合中短上下文下的高质量代理任务。

## 中文译文

这是我的公开笔记中的一条记录。查看权威版本：Qwen3.6-27B。

Qwen3.6-27B 是阿里巴巴集团旗下的通义实验室（Alibaba Cloud）推出的 Qwen 系列中一款原生多模态、全参数激活的稠密型大语言模型，参数量为 270 亿（27B），于 2026 年 4 月 22 日正式发布。该模型定位为“单块高端消费级 GPU 即可运行的旗舰级模型”，在产品线中与更小规模的混合专家模型（MoE）Qwen3.6-35B-A3B，以及仅限 API 调用的 Qwen3.6-Plus / Qwen3.6-Max-Preview 并列。其最引人注目的成果是：在所有主流智能体编程（agentic coding）基准测试中，全面超越上一代 MoE 旗舰模型 Qwen3.5-397B-A17B（总参数量 3970 亿，每次推理激活 170 亿参数），同时磁盘占用体积缩小约 14 倍。

架构特点

• 稠密型 27B 参数 Transformer 架构（非 MoE）：每个 token 推理时均激活全部参数，区别于其 MoE 兄弟型号 Qwen3.6-35B-A3B。

• 原生多模态能力：单一统一权重检查点，支持文本、图像与视频输入；具备视觉-语言联合推理、文档理解及视觉问答（VQA）能力。

• 可切换的“思考模式”与“非思考模式”（契合《AI 推理模型》一文中所记载的推理范式收敛趋势）；支持 preserve_thinking 功能，在智能体任务中跨轮次保留完整推理链。

• 原生上下文窗口：依据官方部署配置为 128K（即 131,072 个 token）；基准测试中已验证支持最高达 256K 上下文长度。

• 默认最大输出长度：16,384 个 token。

• 开源权重：通过 Hugging Face 与 ModelScope 平台分发。

为何重要？

• 将前沿性能压缩至 27B 稠密模型：在 Simon Willison 的对比测试中，该模型在所有主流智能体编程基准上均超越前代 397B 总参数量 / 17B 激活参数的 MoE 旗舰模型，磁盘体积仅为 55.6 GB，相较后者 807 GB 显著精简。

• 无 MoE 路由复杂性：稠密架构简单直接，可使用任意标准推理栈轻松部署与服务；无需专家路由调优、无需辅助负载均衡、无需主机内存协同调度。

• 本地化智能体编程成为现实：采用 Q4_K_M 量化后体积仅 16.8 GB，足以在单块 24 GB 显存的消费级 GPU 或最新款 Apple Silicon 设备上运行，且仍能提供 Simon 测试所确认的“旗舰级智能体编程性能”。

• 稠密模型 vs MoE 模型的权衡再审视：Hacker News 讨论指出，类似质量的稠密模型（如本模型）在上下文长度超过 32–64K 后，性能衰减幅度通常大于同级 MoE 模型。因此，若追求短至中等长度上下文（<32K）下每活跃参数的极致质量，27B 是更优选择；而若活跃计算资源（active-compute budget）更为关键，则应优先选用其 MoE 兄弟型号 35B-A3B。

• Claw-Eval Pass^3：60.6（表中最高分，超越 Claude 4.5 Opus 的 59.6）

• GPQA Diamond：87.8  
• AIME26：94.1  
• HMMT Feb 25 / Nov 25 / Feb 26：93.8 / 90.7 / 84.3  
• LiveCodeBench v6：83.9

• MMLU-Pro：86.2；MMLU-Redux：93.5；SuperGPQA：66.0；C-Eval：91.4

• MMMU：82.9；MMMU-Pro：75.8；MathVista mini：87.4；DynaMath：85.6；VlmsAreBlind：97.0

总体规律：Qwen3.6-27B 在智能体编程任务上全面领先或持平于其他稠密模型及前代 397B MoE 模型；在编程能力上紧追 Claude 4.5 Opus，但在知识类与 HLE 风格的高难度推理任务上略逊于后者。

本地运行性能（Simon Willison 实测数据）  
使用 llama-server（基于 llama.cpp）加载 Q4_K_M Unsloth 量化版本，启用推理模式，上下文长度设为 65,536 token：

• 阅读（prefill）速度：54.32 tokens/s  
• 生成（decode）速度：约 25 tokens/s  

其他 Hacker News 用户报告数据：

• RTX 5090 显卡，Q6_K 量化，123K 上下文：约 50 tokens/s  
• 苹果 M 系列芯片设备，8-bit 量化：8–11 tokens/s  
• Q4_K_M 量化相比全精度仅带来约 1–3% 的困惑度（perplexity）上升，但内存占用减半，被广泛视为该模型的默认最优量化方案。

量化方案全景

• Q4_K_M（约 16.8 GB）：默认推荐方案，质量损失极小。  
• Q6_K：质量显著提升，可在 24 GB 显存卡上运行（需适当缩减上下文长度）。  
• Q8_0：接近全精度质量，适用于对输出质量要求严苛的关键任务。  
• 3-bit 量化变体：适用于内存极度受限场景，但质量下降明显，需谨慎权衡。

部署方式

• 自托管（Self-hosting）：模型权重已发布于 Hugging Face 与 ModelScope；兼容 llama.cpp、vLLM、LM Studio、Ollama 等主流推理框架。  
• 托管 API：阿里云 Model Studio（DashScope 接口，覆盖北京、新加坡、美国弗吉尼亚节点）。  
• API 协议：兼容 OpenAI 标准的聊天补全接口；另提供 Anthropic 兼容接口：https://dashscope-intl.aliyuncs.com/apps/anthropic 。  
• 编程智能体集成：OpenClaw（原 Moltbot / Clawdbot）、Claude Code（通过 Anthropic 协议，设置 ANTHROPIC_MODEL=qwen3.6-27b）、Qwen Code（npm 包 @qwen-code/qwen-code）。  
• 交互式体验：Qwen Studio。

业界反响与注意事项

Simon Willison 称其本地运行效果为“一款仅 16.8GB 的本地模型所取得的卓越成果”，并通过反复进行 SVG 生成测试（如“骑自行车的鹈鹕”“骑电动滑板车的负鼠”）加以验证——模型不仅输出技术正确，且细节丰富、富于创意。

Hacker News 讨论中提出两点值得持续关注的问题：  
• “病毒式基准测试”的古德哈特效应（Goodhart on viral benchmarks）：“骑自行车的鹈鹕”测试已广为人知，前沿模型可能已被隐式调优以适配该任务；切勿将单提示（single-prompt）的“感觉良好”测试结果当作实证依据，仅宜视作轶事参考。

• 短至中等长度上下文任务（< ~32K tokens），且偏好稠密模型行为特性。
