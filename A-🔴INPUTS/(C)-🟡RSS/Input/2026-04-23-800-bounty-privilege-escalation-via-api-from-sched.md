> [!example] AI 摘要
> 该文章描述了一位安全研究员在SaaS平台ExampleCenter中发现的严重Broken Access Control（越权访问）漏洞：低权限的Scheduler用户可通过直接调用后端API绕过UI限制，执行仅限Editor/Admin角色的操作，如创建/复制团队、指定团队负责人等。漏洞根源在于后端未对关键API接口实施有效的权限校验，导致完整的权限提升。研究者通过Burp Suite抓包分析并手动构造请求验证了该问题，后续还发现系统缺乏速率限制和团队名称唯一性校验，可能引发服务混乱。该漏洞获$700赏金及$100复测奖励。

<p>Hi Everyone! I recently discovered a <strong>Broken Access Control / Privilege Escalation vulnerability</strong> in a SaaS platform (ExampleCenter) that allowed a low-privileged user (Scheduler role) to perform <strong>editor-level administrative actions</strong> via direct API calls.</p><p>For this discovery, I was awarded a <strong>$700 bounty along with a $100 bonus for retesting</strong>. Let’s explore how this bug worked, how I exploited it, and why it was important.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*cbYz3K-TO6DoOCJ7TI1jIA.png" /></figure><h3>Understanding the Target</h3><p>ExampleCenter is a SaaS platform used for managing teams, scheduling, and workflows within organizations. It follows a role-based access control model:</p><ul><li><strong>Editors/Admins</strong> → Can manage teams, structure, and permissions</li><li><strong>Schedulers</strong> → Can only assign people to existing teams</li></ul><p>To maintain proper security boundaries, only <strong>Editors and Admin </strong>should be able to:</p><ul><li>Create teams</li><li>Copy teams</li><li>Assign team leaders</li><li>Modify team configurations</li></ul><p>The UI correctly enforces this restriction by displaying:</p><blockquote><em>“Only editors can create teams.”</em></blockquote><p>At this point, everything looked correct.</p><p>But from experience, I’ve learned one important thing:</p><blockquote><em>If something is blocked in the UI… it doesn’t mean it’s blocked in the backend.</em></blockquote><figure><img alt="" src="https://cdn-images-1.medium.com/max/608/1*cOsPe3LpG6I9Cs6gKvA5ZA.png" /></figure><h3>The Moment of Curiosity</h3><p>Instead of stopping there, I opened Burp and started looking at how the application was communicating with the backend.</p><p>I noticed that when switching tabs or loading team-related data, the app was calling certain API endpoints. That gave me an idea:</p><p><em>What if the team creation functionality still exists in the API, but is just hidden in the UI?</em></p><p>So I decided to test it manually by accessing the team creation api from higher level user account and use via scheduler user.</p><h3>The Flaw: Backend Didn’t Enforce Authorization</h3><p>I crafted a request to the team creation endpoint using my <strong>Scheduler account token</strong>:</p><pre>POST /api/services/v2/service_types/{id}/teams HTTP/2<br />Host: api.examplecenter.com<br />Authorization: Bearer &lt;scheduler_token&gt;<br />Content-Type: application/json<br /><br />{<br />  &quot;data&quot;: {<br />    &quot;type&quot;: &quot;team&quot;,<br />    &quot;attributes&quot;: {<br />      &quot;name&quot;: &quot;SchedulerTeam&quot;,<br />      &quot;copy_team_members&quot;: true,<br />      &quot;secure_team&quot;: true,<br />      &quot;team_leader_ids&quot;: [attacker_id]<br />    }<br />  }<br />}</pre><p>I honestly expected a <strong>403 Forbidden</strong>.</p><p>But instead…</p><p>👉 <strong>200 OK — Team Created Successfully</strong></p><p>Not only that:</p><ul><li>The team was created</li><li>I was assigned as <strong>Team Leader</strong></li></ul><p>At that moment, it was clear:</p><blockquote><em>This wasn’t just a UI issue — this was a full authorization bypass.</em></blockquote><h3>Going Deeper: How Far Can This Go?</h3><p>Once I confirmed the initial bug, I started exploring how much control I actually had.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/628/1*IK7ykme5TcloKxNJ_IXJxQ.png" /></figure><h3>1. Copy Existing Teams</h3><p>I noticed a parameter:</p><pre>&quot;copy_from&quot;: &quot;&lt;team_id&gt;&quot;</pre><p>So I tried cloning an existing team.</p><p>👉 Result:</p><ul><li>Full team structure copied</li><li>Members and configurations inherited</li><li>I could assign myself as leader</li></ul><p>This turned the bug from <strong>simple bypass → structured privilege escalation</strong></p><h3>2. Assigning Leadership</h3><p>By modifying:</p><pre>&quot;team_leader_ids&quot;: [my_user_id]</pre><p>I could:</p><ul><li>Assign myself as leader</li><li>Assign other users as leaders</li></ul><p>👉 Basically controlling hierarchy inside the system</p><h3>3. Mass Team Creation</h3><p>Then I tested limits…</p><ul><li>No rate limiting</li><li>No restrictions</li></ul><p>👉 I could create <strong>hundreds of teams quickly</strong></p><p>This could:</p><ul><li>Flood the system</li><li>Break workflows</li><li>Create administrative chaos</li></ul><h3>4. Duplicate Team Names</h3><p>Another small but interesting issue:</p><ul><li>Same team name allowed multiple times</li><li>No uniqueness validation</li></ul><p>👉 Leads to confusion + potential misuse</p><h3>Root Cause</h3><p>This bug came down to one classic mistake:</p><blockquote><strong><em>Authorization was enforced only in the UI, not in the backend API</em></strong></blockquote><ul><li>UI → correctly restricts Scheduler</li><li>API → blindly accepts request</li></ul><p>This mismatch is exactly where most <strong>BAC (Broken Access Control)</strong> bugs live.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/632/1*kkbKjniQRm8dTL5spd1-Wg.png" /></figure><h3>Impact</h3><p>This wasn’t just theoretical it had real-world implications:</p><h4>Security Impact</h4><ul><li>Privilege escalation (Scheduler → Admin-like control)</li><li>Unauthorized structural changes</li><li>Self-assigned leadership roles</li></ul><h4>Operational Impact</h4><ul><li>Mass team creation → workflow disruption</li><li>Duplicate teams → confusion</li><li>Increased cleanup overhead</li></ul><h4>Business Risk</h4><ul><li>Breaks trust in role-based permissions</li><li>Violates least privilege principle</li><li>Could enable misuse or internal abuse</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/614/1*3QSRqg0yv5_lEJG60rYfCA.png" /></figure><h3>Bounty &amp; Program Response</h3><ul><li><strong>Reported:</strong> Dec 20, 2025</li><li><strong>Triaged:</strong> Jan 5, 2026</li><li><strong>Severity:</strong> High → Medium</li><li><strong>Bounty:</strong> $700 + $100 bonus</li><li><strong>Retest:</strong> Fix confirmed (API now returns 403)</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*yZZJOErxipdwHS1z17XUOA.png" /></figure><h3>Key Takeaways</h3><ul><li>Never trust UI restrictions always test the API</li><li>Backend authorization is the <strong>real security layer</strong></li><li>Privilege escalation often hides in: Create , Copy ND Assign operations</li><li>Missing rate limits can amplify impact</li><li>Observing API calls / JS endpoints can reveal hidden attack surfaces</li></ul><h3>Conclusion</h3><p>This bug is a perfect example of how <strong>frontend restrictions can create a false sense of security</strong>.</p><p>From the UI, everything looked secure.</p><p>But under the hood, the API allowed a low-privileged user to perform <strong>admin-level actions</strong>.</p><p>These kinds of vulnerabilities are extremely common in modern SaaS platforms — especially where complex role systems exist.</p><p>As a hunter,
