<figure><img alt="" src="https://cdn-images-1.medium.com/max/887/1*KasAQhh6vEclehnhMQ1EMg.png" /></figure><h3>1. Entry Point: Phone Verification (KYC) Bypass</h3><p>The application enforces a mandatory phone verification step after registration at a specific gate. However, this was implemented as a weak client-side redirect.</p><ul><li><strong>Vulnerability:</strong> Broken Access Control / Bypass.</li><li><strong>Methodology:</strong></li></ul><ol><li>Register a new account.</li><li>Intercept the redirect to the verification endpoint.</li></ol><p><strong>https://test.com/public/kyc-approval?customerId=X&amp;redirect_uri=/public/profile</strong></p><ol><li>Manually modify the URL to the user profile path and stop the page load before the redirect triggers.</li></ol><p><a href="https://test.com/public/profile"><strong>https://test.com/public/profile</strong></a></p><p>To make it persistent, I used Burp’s rule to automatically swap the verification URL with the profile URL in every outgoing request.</p><ul><li><strong>Result:</strong> Full access to the authenticated user dashboard without completing the required KYC process.</li></ul><h3>2. Deep Dive: Authenticated Time-Based SQL Injection</h3><p>Once the KYC gate was bypassed, I analyzed the authenticated API traffic. An endpoint used for managing records caught my attention due to its parameter handling.</p><ul><li><strong>Target Endpoint:</strong> POST <a href="">https://api.[REDACTED].com/api/case</a></li><li><strong>Vulnerable Parameter:</strong> …Id</li><li><strong>Payload:</strong> 'XOR(if(now()=sysdate(),sleep(4),0))XOR'Z</li><li><strong>Observation:</strong> The server responded with a consistent 4-second delay, confirming that the backend was executing the injected SQL command.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*XA5tgpytcEpUOpqaPmw8mA.png" /></figure><h3>3. Expanding the Attack Surface: Double IDOR (Create &amp; Delete)</h3><p>The lack of proper authorization checks extended to object-level references, allowing for complete manipulation of other users’ data.</p><h4>A. Unauthorized Record Creation</h4><ul><li><strong>Vulnerability:</strong> IDOR in the owner identification parameter.</li></ul><p><strong>Exploit:</strong> By modifying the ....Id in the POST /api/case request (e.g., from my ID to a victim’s ID), I could create or update records on behalf of any user.</p><h4>B. Unauthorized Record Deletion</h4><ul><li><strong>Vulnerability:</strong> IDOR in the delete endpoint.</li></ul><p><strong>Exploit:</strong></p><ol><li>Intercept the delete request: POST /api/case/[ID]/delete.</li><li>Change the object ID to a victim’s ID.</li></ol><ul><li><strong>Result:</strong> The system deleted the victim’s record without verifying if the authenticated user was the actual owner.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/229/1*xa6rwGQZsgtH_62mTAuuSg.png" /></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/223/1*rf_KhLFL9DYDR_WmoQY6mw.png" /></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/218/1*Fgv6hNTwCxPb8WGgIwuAFQ.png" /></figure><h3>Stay Connected</h3><ul><li><strong>X (Twitter):</strong> <a href="https://x.com/xelcezeri">@xelcezeri</a></li><li><a href="https://www.linkedin.com/in/xsametyigit/"><strong>LinkedIn:</strong> Samet Yiğit</a></li></ul><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=0425f362dad5" width="1" />
