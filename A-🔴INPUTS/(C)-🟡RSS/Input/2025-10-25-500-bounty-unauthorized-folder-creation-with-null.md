> 该文章描述了一位安全研究员在SaaS招聘平台发现的一个简单但影响严重的漏洞：通过API请求将文件夹名称设为`null`，绕过前端验证，导致后端创建了一个无名称文件夹。由于系统无法处理空名称，该文件夹对所有用户（包括创建者和协作者）完全不可见、不可访问，造成持久性拒绝服务（DoS）和数据锁定。尽管漏洞利用简单，仅需修改JSON中的`"name": null`，仍被项目方认可并授予500美元赏金，凸显了输入验证缺失的严重后果。

<p>Hey everyone, In this write-up, I’ll share a <strong>simple but impactful bug</strong> I found in a <strong>SaaS recruitment platform</strong> that allowed me to create a folder with a null name.</p><p>The result? The folder became <strong>completely inaccessible</strong> to all users — including the attacker and legitimate collaborators — effectively causing a <strong>denial-of-service (DoS)</strong> for that project.</p><p>For this bug, I was awarded a <strong>$500 bounty</strong>. \</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*x4UM7QqdQN6OlsSEA55g1A.png" /></figure><h3>Understanding the Feature</h3><p>The platform allows users to create folders, share them with others, and manage candidates or projects collaboratively.</p><p>Normally, folders require a valid string name to function. But during testing, I discovered that the backend didn’t enforce strict validation on the <strong>name field</strong>.</p><p>This oversight opened the door for a quirky but impactful issue.</p><h3>The Flaw: Null Folder Name</h3><p>By intercepting the API request during folder creation or update, I noticed that the name field could be manipulated.</p><p>Original request while creating a folder:</p><blockquote>PUT /api/recruiter/cart/1f378efc-4bd4–4691-ac78-acf19371da88 HTTP/2<br />Host: app.examplecorp.com<br />Content-Type: application/json</blockquote><blockquote>{<br /> “name”: “Test Folder”,<br /> “description”: “”,<br /> “jobDescriptionUrl”: “”<br />}</blockquote><p>I modified the payload to set “name”: null:</p><blockquote>PUT /api/recruiter/cart/1f378efc-4bd4–4691-ac78-acf19371da88 HTTP/2<br />Host: app.examplecorp.com<br />Content-Type: application/json</blockquote><blockquote>{<br /> “name”: null,<br /> “description”: “”,<br /> “jobDescriptionUrl”: “”<br />}</blockquote><p>Response: 200 OK — folder successfully updated.</p><h3>Verifying the Issue</h3><ul><li>When I navigated back to the UI, the folder was <strong>no longer accessible</strong>.</li><li>Other authorized users also couldn’t access or manage it.</li><li>Since the system had no valid identifier for the folder name, it effectively broke access for everyone.</li></ul><p>This created a <strong>persistent denial-of-service (DoS)</strong> for that shared resource</p><h3>Impact</h3><ul><li><strong>Denial-of-Service</strong> → A project or shared folder could be made permanently inaccessible.</li><li><strong>Data Lockout</strong> → Users lost access to their stored candidates, notes, or shared resources inside the folder.</li><li><strong>Improper Input Validation</strong> → Backend trusted null without sanitizing it.</li></ul><h3>Timeline</h3><ul><li><strong>Day 1</strong> — Report submitted.</li><li><strong>Day 5</strong> — Initially marked out of scope (DoS).</li><li><strong>Same Day</strong> — Reopened for program review.</li><li><strong>Later</strong> — Triaged and $500 bounty awarded 🎉.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/294/1*39EaUPL42Xiu6FkGez6GdQ.png" /></figure><h3>Lessons Learned</h3><ul><li>Even small validation issues can lead to real impact.</li><li>Always sanitize input values before processing.</li><li>Don’t assume “simple” bugs won’t be rewarded — this one earned me $500 despite being easy to exploit</li></ul><h3>Final Thoughts</h3><p>This was a great reminder that <strong>low-effort tests can sometimes reveal high-value issues</strong>.</p><p>If you’re hunting:</p><p>👉 Try sending
