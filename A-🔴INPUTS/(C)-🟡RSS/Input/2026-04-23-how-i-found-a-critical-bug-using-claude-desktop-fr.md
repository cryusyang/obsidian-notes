<p><strong>TL;DR:</strong> I fed a JavaScript bundle to <strong>Claude Desktop </strong>(I use Burp MCP with Claude). It mapped hidden endpoints I’d missed after multiple reviews. That single nudge led me down a rabbit hole: predictable user IDs leaking PII of high-profile individuals, and write operations that allowed fund redirection, email hijacking, and balance manipulation. The AI didn’t find the bug — but it handed me the flashlight.</p><p><em>Fun fact: I had reviewed this JavaScript file multiple times before without catching the vulnerable endpoint. It wasn’t until I fed the code to </em><strong><em>Claude </em></strong><em>that it mapped out the endpoint structure and helped me craft a valid request. The AI didn’t find the vulnerability itself — but it gave me the exact lens I needed to see what had been hiding in plain sight all along.</em></p><h3>The Target</h3><p>A private bug bounty program for a fitness company. Think celebrities, athletes, and executives as users. The platform handles memberships, payouts, and partner programs — real money flowing through real APIs.</p><p>The program name stays redacted. You know the rules.</p><h3>Step 1: Let the AI Read What I Couldn’t See</h3><p>I’m a firm believer in reading JavaScript manually. Automated scanners are great, but they don’t <em>think</em>. The problem? Sometimes neither do I — at least not after staring at the same minified bundle for the third time.</p><p>So I tried something different. I dropped the JS file into Claude and asked it to analyze the code, enumerate API endpoints, craft request and identify anything interesting.</p><p>Within seconds, it came back with a structured breakdown: endpoint paths, HTTP methods, parameter schemas, and even built me a valid POST request to test one particularly juicy route tied to a financial feature.</p><p>I had literally been looking at this same code. Multiple times. And missed it.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/774/1*UyhbxUOpTC59hq2eWqXALg.png" /></figure><p>Lesson learned: <strong>sometimes a second pair of eyes doesn’t need to be human.</strong></p><h3>Step 2: The IDOR — “Wait, That’s Not My Account”</h3><p>Armed with the AI-crafted request, I hit the endpoint using my own account ID — a simple numeric value. The response was generous:</p><pre>→ Full name<br />→ Email address<br />→ Bank account identifier<br />→ Account balance<br />→ Internal account status</pre><figure><img alt="" src="https://cdn-images-1.medium.com/max/1010/1*p4iVv_yXz_7GLe2qMeoY7w.png" /></figure><p>Cool. Now let me just change that ID by one…</p><p>Same data. Different person. No authorization check. The server didn’t care <em>who</em> was asking — only <em>what</em> ID was provided.</p><p>I kept incrementing. Every single request returned a complete profile with financial details. And the accounts I was seeing? These weren’t test users. These were <strong>high-profile individuals</strong> — the kind of people whose data breach makes headlines.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/483/1*ZHGMErDEPJfMM3Z4WVyDvw.png" /></figure><h3>Step 3: “Can I Write Too?” — Spoiler: Yes</h3><p>A read-only IDOR is already critical when you’re leaking bank details of public figures. But I wanted the full picture.</p><p>I went back to the AI assistant, this time asking it to help me understand which parameters the endpoint would accept for modification. It helped me map the writable fields based on the JS source.</p><p>Then I tested three things:</p><p><strong>Fund Redirection</strong> — I modified the bank account parameter. The server accepted it. Just like that, payouts could be rerouted to any account. Mine, yours, anyone’s.</p><p><strong>Email Hijacking</strong> — Changed the email field on a target account. Now trigger a password reset, catch it on your inbox, and you own the account. Classic, devastating, and entirely preventable.</p><p><strong>Balance Manipulation</strong> — This one surprised even me. The balance field was writable. I could set it to zero. I could set it to a million. The server said “sure, sounds good” every single time.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*spuaEMt3oovQVrrmwT6u8A.png" /></figure><h3>The Kill Chain</h3><pre>Read JS with AI assistance → Discover hidden endpoint + valid request structure<br />      ↓<br />Send POST with sequential ID → Full PII of any user<br />      ↓<br />Enumerate IDs → Mass data exfiltration<br />      ↓<br />Modify bank account → Redirect funds<br />Modify email → Account takeover<br />Modify balance → Financial fraud</pre><p>One JavaScript file. One AI conversation. Total compromise.</p><h3>Why This Happened</h3><p>Three classic failures stacked on top of each other:</p><p><strong>No authorization.</strong> The API trusted the client to only ask for its own data. Spoiler: attackers don’t follow the honor system.</p><p><strong>Predictable IDs.</strong> Sequential integers as user identifiers. Enumeration was as simple as a for loop.</p><p><strong>Mass assignment.</strong> The API let clients write to fields that should never be client-controlled — bank accounts, emails, balances. No allowlist, no validation, no separate workflow for sensitive changes.</p><h3>The AI Factor</h3><p>I want to be transparent about this because I think it matters for the community.</p><p>The AI didn’t “hack” anything. It didn’t exploit the vulnerability or even flag it as a security issue. What it did was <strong>process information faster and more systematically than I could on my fourth pass through minified JavaScript.</strong></p><p>It enumerated every endpoint, organized them by HTTP method, identified parameter structures, and built me a working request. That’s the kind of grunt work that usually takes an hour of squinting at obfuscated code — done in seconds.</p><p>The vulnerability discovery, the intuition to test for write access, the escalation strategy — that was all human judgment. But the starting point? That came from an AI reading code I’d already given up on.</p><p><strong>If you’re not using AI as part of your recon workflow, you’re leaving bugs on the table. In my case a 4 digits bug.</strong></p><figure><img alt="" src="https://cdn-images-1.medium.com/max/643/1*F_QODV-wvwa4XMrc3s5Z2A.png" /></figure><h3>Final Thoughts</h3><p>Read the JavaScript and go deep in your target. If you’ve already read it — feed it to an AI and read it again. The bugs aren’t hiding in the code you haven’t seen. They’re hiding in the code you’ve already looked at and dismissed.</p><p>After this i definitely bought Claude Pro subscription.</p><p>And when you find a read, always check for a write. That’s where the severity jumps from “interesting” to “bugbounty journey-defining.”</p><p>Happy hunting.</p><p><em>If you found this write-up useful, feel free to connect with me.
