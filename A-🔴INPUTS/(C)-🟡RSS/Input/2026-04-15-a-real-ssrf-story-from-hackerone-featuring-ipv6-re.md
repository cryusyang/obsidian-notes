<p>In the world of web security, even the most seemingly harmless features like webhooks can hide critical vulnerabilities. In this article, we take a deep dive into a <strong>Server-Side Request Forgery (SSRF)</strong> bug discovered in a webhook implementation. What made this case especially interesting is that exploitation was only possible by chaining <strong>IPv6</strong> behavior with <strong>redirection </strong>tricks. Here’s a technical breakdown of how my good friend <a href="https://hackerone.com/madara_"><em>madara_ </em></a>and <a href="https://hackerone.com/red_darkin"><em>I</em></a> identified and exploited this vulnerability.</p><p>In modern applications, features like webhooks are everywhere. They enable automation, integrations, and real-time workflows.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*2idgc4z5_W9OwGh5Ug1p5A.png" /><figcaption>Vulnerable feature</figcaption></figure><p>But they also introduce something dangerous:</p><blockquote><strong><em>You are letting your server make requests on behalf of the user.</em></strong></blockquote><p>And that’s exactly where things start to break.</p><p>This is the story of how a seemingly “secure” webhook implementation led to a <strong>Server-Side Request Forgery (SSRF) </strong>using a combination of <strong>IPv6 encoding </strong>and <strong>redirect abuse</strong>.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/923/1*g52wwpPbD78u3-wykfvczA.png" /></figure><p><strong>First, What is SSRF (Quickly) …</strong><br />A Server-Side Request Forgery happens when an attacker tricks a server into sending requests to unintended destinations, such as:</p><ul><li>Internal services (127.0.0.1)</li><li>Private APIs</li><li>Cloud metadata endpoints</li><li>Admin interfaces</li></ul><p>Instead of attacking directly, you let the server do the work for you.</p><h4>The Entry Point: A Webhook Feature</h4><p>While testing a target on HackerOne, we found a webhook functionality. Nothing unusual. Until we noticed:</p><ul><li>It accepted user-controlled URLs</li><li>It triggered server-side requests</li><li>It had some filtering in place</li></ul><p>At first glance, it looked hardened.</p><h4>Initial Behavior</h4><p>The application had protections:</p><ul><li>Blocking internal IPs in decimal format (like 127.0.0.1)</li><li>Filtering common SSRF payloads</li><li>Allowing redirection but still blocking internal IPs in decimal format</li></ul><p>So… no direct SSRF.</p><p>But then we focus test something simple: <strong>Redirects</strong></p><figure><img alt="" src="https://cdn-images-1.medium.com/max/701/1*OssJE5O4VaxtmhCqR4aWFQ.png" /></figure><p>We discovered the backend followed redirects automatically but it did not re-validate the destination, this is a classic mistake, so instead of targeting internal resources directly, we tried:<br /><a href="http://attacker.com"><em>http://attacker.com</em></a> → redirect → internal resource (decimal) → Still blocked.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/665/1*0vTojFgVh6ttUXqJ5hllow.png" /></figure><p>So we went deeper.</p><h4>The Breakthrough: IP Representation Tricks</h4><p>Filters often block this:<br />127.0.0.1</p><p>But forget that the same IP can be written differently.<br />[::ffff:7f00:1]</p><p>This is basically encode IPv4 as IPv6… And the filter? didn’t catch it.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/316/1*JEcMV81d-pMQ57w68A68mw.png" /><figcaption>Full Exploit Chain</figcaption></figure><p>This is the redirector file we used to check the vulnerability exists.</p><pre>&lt;?php<br />header(&quot;Access-Control-Allow-Origin: *&quot;);<br />header(&quot;Access-Control-Allow-Methods: GET, POST, PUT, DELETE&quot;);<br />header(&quot;Access-Control-Allow-Headers: Origin, X-Requested-With, Content-Type, Accept&quot;);<br />header(&quot;Content-Type: application/json&quot;);<br />header(&quot;Location: http://[::ffff:a9fe:a9fe]&quot;);<br />?&gt;</pre><figure><img alt="" src="https://cdn-images-1.medium.com/max/937/1*Jj7uUSA7_S0JKWSqfmt5iw.png" /><figcaption>Moment when we realized the SSRF was possible.</figcaption></figure><p>Once we realized we had a window into the internal infrastructure, the obvious next step was clear: port scanning, but the system had other plans.</p><p>The webhook responses were painfully inconsistent… delays everywhere, no reliable timing, no clean signals. Open ports, closed ports… everything looked the same. Automation was useless.</p><p>So we adapted.</p><p>Instead of relying on tools, we went manual; slow, deliberate, and focused. We started probing well-known ports one by one, looking for anything that behaved differently.</p><p>It wasn’t fast. But it worked.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*aquvlYyKS8pnn0hm1pKJ4Q.png" /></figure><p><strong>Open ports discovered:</strong></p><ul><li>5000</li><li>5012</li><li>8090</li><li>8126</li><li>24220</li></ul><p>This is where things get interesting. Internal services often expose:</p><ul><li>Debug endpoints</li><li>Admin panels</li><li>Internal APIs</li><li>Metrics systems</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/981/1*fnDYDPIkNM_1rSnU9bD_Qw.png" /></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*OT7dcojSx1AcTvSNXllc2Q.png" /></figure><p>Along the way, we also discovered that even after the redirect, it was still possible to bypass the filtering mechanisms using alternative IP representations like octal and IPv6.</p><p>To streamline the exploitation, we ended up using a payload like:</p><p>https://ourserver/h1/redirector.php?url=http://[::ffff:7f00:1]:§5000§</p><p>This bug wasn’t about breaking a system. It was about understanding it better than it understands itself. The filter didn’t fail because it was weak, it failed because it was incomplete.</p><h3>Timeline</h3><ul><li>Jan 2, 2024 — Report submitted</li><li>Jan 3 — “Need more info”</li><li>Jan 8 — Triaged</li><li>Jan 9 — “Please don’t escalate further…” 😅</li><li>Jan 10 — Severity downgraded</li><li>Jan 16 — $2,500 bounty</li><li>Jan 30 — Disclosure [Report <a href="https://hackerone.com/reports/2301565"><em>Here</em></a>]</li></ul><p>More detailed slides about SSRF bypass Techniques click <a href="https://github.com/Red-Darkin/h1-Comunity-Colombia---Slides/blob/main/SSRF.pdf"><em>here</em></a></p><h3>Credits</h3><p>Big shoutout to <a href="https://hackerone.com/madara_"><strong>madara_</strong> </a>for teaming up on this one.</p><p>And remember It’s never just about the bug, it’s about how far you can push it.</p><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=9aa5e2ad8c2e" width="1" />
