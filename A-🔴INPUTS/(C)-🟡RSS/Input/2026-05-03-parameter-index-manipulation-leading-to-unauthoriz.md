> 该文章描述了一种因服务端验证缺失导致的表单字段注入漏洞：目标内部社区平台使用索引式参数（如_0、_1、_3）提交表单，但未校验索引连续性与合法性，攻击者可手动添加缺失索引（如_2）注入并篡改本不应暴露的敏感字段（如邮箱、角色、姓氏等）。漏洞成因在于依赖不安全的索引映射且缺乏服务端字段白名单校验，可能导致数据完整性破坏、越权操作甚至权限提升。作者通过Burp Suite复现并验证了该问题，报告已获HackerOne项目方确认。

<h3>Introduction</h3><p>Hi everyone,</p><p>In this write-up, I will explain an interesting vulnerability I discovered in a private program on HackerOne. The issue allowed me to inject and manipulate unintended fields during form submission due to improper server-side validation.</p><h3>Application Overview</h3><p>The target application is an internal community platform used within organizations. It allows employees to:</p><ul><li>Share posts</li><li>Participate in voting</li><li>Submit structured forms</li></ul><p>One of the key features is the <strong>Forms functionality</strong>, where administrators define specific fields (such as name, email, role, and custom attributes) to collect structured data from users.</p><p>Ideally, users should only be able to submit values for predefined fields controlled by the form configuration.</p><h3>Vulnerability Discovery</h3><p>While testing the form submission functionality, I noticed something unusual in the HTTP request structure.</p><p>Instead of descriptive parameter names, the application used indexed parameters such as:</p><ul><li>_0 → Input field</li><li>_1 → Date field</li><li>_3 → Another field</li></ul><p>However, I observed that _2 was missing entirely.</p><p>This inconsistency suggested that the backend might rely on index-based mapping without strict validation.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*LLTAk4KxNWpTYvSBibOklA.png" /></figure><h3>Exploitation</h3><p>To test this behavior, I intercepted the request using Burp Suite and manually added the missing parameter:</p><pre>_2 = injected_value</pre><p>After sending the modified request, the server:</p><ul><li>Accepted the new parameter</li><li>Processed it without validation</li><li>Reflected the injected value in the application</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*rwWKyazdMMWFQ1f4YnPvug.png" /></figure><h3>Impact</h3><p>This vulnerability allows an attacker to manipulate form submissions beyond intended restrictions. Specifically, I was able to:</p><ul><li>Modify fields that were not exposed in the original form</li><li>Inject values into hidden or restricted fields</li></ul><p>Alter sensitive attributes such as:</p><ul><li>Last Name</li><li>Email</li><li>Role</li><li>Additional Information fields</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*0-xjTSK1M9nnrgNIGT12DA.png" /></figure><h3>Security Risk</h3><p>This issue can lead to:</p><ul><li><strong>Data integrity violations</strong></li><li><strong>Unauthorized data manipulation</strong></li><li>Potential <strong>privilege escalation</strong> (if role-based fields are affected)</li></ul><p>In certain scenarios, this could impact business logic and trust in stored data.</p><h3>Root Cause</h3><p>The issue occurs due to:</p><ul><li>Reliance on index-based parameter mapping</li><li>Lack of proper server-side validation</li><li>No enforcement of allowed field indices</li></ul><h3>Conclusion</h3><p>This vulnerability highlights the risks of relying on weak parameter mapping without proper validation. Even a small inconsistency, such as a missing index, can lead to unauthorized data manipulation.</p><p>The report was submitted through HackerOne and successfully acknowledged by the program.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/287/1*ZZL9dSFuw9q46HRGKXZq5A.png" /></figure><p><strong>Thanks for reading!</strong><br />Feel free to reach out if you have any questions or feedback.</p><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=7e830ecfad05" width="1" />
