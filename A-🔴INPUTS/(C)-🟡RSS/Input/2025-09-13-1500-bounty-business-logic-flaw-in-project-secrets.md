<p>Hi everyone, This time I want to share a <strong>Business Logic Vulnerability</strong> I found in a SaaS platform that allowed <strong>Editor-level users</strong> to bypass UI restrictions and directly <strong>add secrets</strong> to projects — something only <strong>Owners</strong> were supposed to do.</p><p>For this report, I was awarded a <strong>$1,500 bounty</strong>. Let’s dive in.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*faUwGZ2cUpLeNyR7rP5eXQ.png" /></figure><h3>Background</h3><p>On this platform:</p><ul><li><strong>Owners</strong> → Full permissions (manage projects, secrets, configurations)</li><li><strong>Editors</strong> → Edit project code/resources, but should not manage sensitive project secrets</li><li><strong>Viewers</strong> → Read-only access.</li></ul><p>Additionally, on <strong>free-tier plans</strong>, the <strong>Manage section</strong> (where secrets are handled) is <strong>not available</strong>.</p><p>So, logically, an <strong>Editor on a free-tier project should never be able to create or update secrets</strong>.</p><p>But the API told a different story.</p><h3>The Vulnerability</h3><p>Even though the <strong>UI prevented Editors from accessing the Manage section</strong>, the backend API still allowed Editors to add secrets <strong>directly</strong> with a crafted request.</p><h3>Proof-of-Concept Reques</h3><blockquote>POST /api/v1/secrets/namespace/project:&lt;project_id&gt;/name/&lt;secret_name&gt; HTTP/2<br />Host: target.com<br />Content-Type: application/json</blockquote><blockquote>{“value”:”csdc”}</blockquote><ul><li>Replace &lt;project_id&gt; with the project UUID.</li><li>Replace &lt;secret_name&gt; with any arbitrary key.</li><li>Forward the request.</li></ul><h3>Response</h3><blockquote>HTTP/2 200 OK<br />{<br /> “message”: “Secret created successfully”,<br /> “name”: “&lt;secret_name&gt;”,<br /> “value”: “csdc”<br />}</blockquote><p>The secret was created under the project namespace.</p><h3>Steps to Reproduce</h3><ol><li>Create or access a <strong>free-tier project</strong> where you are assigned as an <strong>Editor</strong>.</li><li>Observe that the <strong>Manage section</strong> is hidden in the UI.</li><li>Intercept traffic with Burp Suite and send a crafted API request (like the one above).</li><li>Server accepts the request → Secret successfully added.</li></ol><h3>Expected Behavior</h3><p>The API should enforce the same restrictions as the UI:</p><ul><li>Editors should <strong>not</strong> be able to create secrets.</li><li>Free-tier projects should <strong>not</strong> allow secret management at all.</li></ul><p>The correct response should have been:</p><h3>Actual Behavior</h3><ul><li>UI restriction existed</li><li>API restriction was missing</li><li>Editors could <strong>add or alter secrets</strong> despite policy restrictions.</li></ul><h3>Root Cause</h3><ul><li><strong>Mismatch between UI and backend authorization</strong>.</li><li>UI correctly hid the Manage section for Editors / free-tier users.</li><li>API endpoint trusted role metadata incorrectly and allowed requests.</li><li>Lack of <strong>server-side enforcement</strong> → client-side control bypass.</li></ul><h3>Impact</h3><ul><li><strong>Privilege Escalation</strong> → Editors could perform Owner-only actions.</li><li><strong>Policy Violation</strong> → Free-tier limitations bypassed.</li><li><strong>Sensitive Data Risks</strong> → Malicious editors could inject secrets affecting deployments, pipelines, or configurations.</li><li><strong>Misleading UX</strong> → UI indicated that Editors cannot manage secrets, but API contradicted it.</li></ul><h3>Timeline</h3><ul><li><strong>July 5, 2025</strong> — Report submitted (Severity: High, CVSS 8.3).</li><li><strong>July 9, 2025</strong> — Triaged.</li><li><strong>July 10, 2025</strong> — Fix confirmed + $1,500 bounty awarded 🎉.</li></ul><h3>Final Thoughts</h3><p>This bug is a great example of a <strong>Business Logic Vulnerability</strong> — no injection payloads, no
