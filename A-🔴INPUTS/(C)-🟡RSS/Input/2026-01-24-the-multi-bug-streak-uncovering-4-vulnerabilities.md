<figure><img alt="" src="https://cdn-images-1.medium.com/max/653/1*9GFHie9YZm2HiBfjGQq1iw.png" /></figure><p>In bug bounty hunting, there is a golden rule: <strong>The more time you spend on a target, the more its secrets unfold.</strong> Many researchers move on after finding their first bug, but I prefer a “deep dive” approach. Today, I’m sharing how I discovered four different vulnerabilities — ranging from SVG XSS to IDOR — on a single VDP program by simply testing every function.</p><p><strong>Note:</strong> <em>This is a series of vulnerabilities I discovered in early 2024. Due to disclosure policies and timing, I’m only able to share the details with you now.</em></p><h3>Bug 1–2: HTML Injection &amp; XSS via Profile Description</h3><p>My first stop was the /profile section. I started by testing the &quot;Edit Profile&quot; description field with simple characters like 123&lt;&gt;.</p><ul><li><strong>Discovery:</strong> The page source revealed that the input was reflected directly without any filtering or WAF protection.</li><li><strong>Exploitation:</strong> I injected &lt;h1&gt; tags for visual impact and an &lt;a&gt; tag to redirect users. This confirmed that any user visiting the profile would execute my HTML/JS payload.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*baj3ruP3cTh39cEIVFlAKA.png" /></figure><h3>Bug 3: XSS via SVG (Bypassing the Content Filter)</h3><p>The application had a public dashboard where users could create posts. While standard tags like &lt;script&gt; were strictly blocked, I noticed the app allowed <strong>SVG file uploads</strong> for images.</p><ul><li><strong>The Technique:</strong> I prepared a malicious .svg file containing an XSS payload.</li><li><strong>The Result:</strong> Even when security filters are in place for text inputs, file uploads are often overlooked. When the SVG was opened in a new tab or viewed directly, the XSS triggered successfully.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/827/1*RrnbpQPfmt595cbr7qs1qw.png" /></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/803/1*ORV-e-gjSqGqnY3ODVv2UQ.png" /><figcaption><strong>sometimes it doesn’t allow svg, so capture the request with burp and set the file extension to svg.png or you can try changing the content type header</strong></figcaption></figure><h3>Bug 4: IDOR — Unauthorized Post Deletion</h3><p>This was the most critical finding. While interacting with the dashboard, I captured a “Delete Post” request using Burp Suite.</p><ul><li><strong>The Attack:</strong> I identified the POSTID parameter. I then initiated a deletion for my own post but swapped my ID with a victim's POSTID.</li><li><strong>Result:</strong> The server failed to verify ownership, allowing me to delete any post on the platform.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/915/1*MjCqGVuOu2y85405HyiqWA.png" /></figure><p>Out of 4 reports, 3 were accepted immediately. This experience reinforced a key lesson: Don’t just scratch the surface. If you find one bug, keep digging.
